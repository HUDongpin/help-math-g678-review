# Measured G6–G8 engineering improvements

Use this reference when an observed G6–G8 bottleneck justifies changing a shared
reader, validation batch, extraction cache or execution workflow. It supplements
[current-js-throughput.md](current-js-throughput.md); normal page implementation
continues through that workflow without a separate research phase.

## Choose the cost that matters

Join the actual active index, registry and workflow events before estimating
remaining work. Progress Markdown and generated queue counts can lag a real
registration. Report registered placements, dated integrated-event claims and
known unfinished registered units separately; an absent current full-denominator
validation count is unknown, not zero or the registry count.

Profile the complete segment proposed for improvement, including repeated calls
from common admission, formal readers and actual semantic validators. Record
read calls/bytes and process wall time beside stage time. Read current code and
recent receipts first: the common reader may already deduplicate pin verification
inside each async admission call. Extending its lifetime over a complete formal
operation is different from adding the same cache again.

Use measured absolute savings to select the intervention. A parser optimization
that saves milliseconds does not resolve a workflow spending minutes on repeated
validation and hours on implementation/browser work. Keep unknown portions of
unit time unknown; do not assign them to source recovery or model reasoning by
subtraction. New extraction tools still need source-specific output comparison.
Source-generated TypeScript plus a maintained runtime/host bridge is the
adopted HFR implementation path; standalone player/emulator success alone does
not establish product integration. Prioritize the missing step in the
[lesson delivery loop](current-js-throughput.md#lesson-batches-and-separate-delivery-gates)
over another local optimization that leaves generated candidates unintegrated.

## Compare the real path fairly

Keep the original failure when a baseline cannot run. If a correctness repair is
needed, apply the same reviewed repair to both arms and measure the optimization
against that repaired baseline. For example, a formal reader's exact proof path
must match its active index entry; do not remove the equality assertion or count
fixing it as a cache speedup.

Run the actual maintained caller and its semantic validators on a representative,
a second real consumer and a repeat batch of at most five suitable consumers.
This is an initial optimization experiment, not a cap on calibrated lesson
production. Retain page-specific source assertions. Reverse A/B order for the repeat when
practical; record every run, failure and input change. A few runs establish an
observed range, not statistical certainty or whole-project throughput.

Bind the actual working files, transitive code/data inputs, tool versions and
benchmark harness at start and finish. When another task owns the active dirty
worktree, take the smallest required verified closure into an isolated output
volume. A clean Git checkout may omit the needed implementation. Copy ordinary
files with before/after metadata and content checks; explicitly bind remaining
external inputs. Isolated code execution does not imply all source/evidence
reads are isolated. Check the actual workspace-package resolution graph when
reusing a physical node_modules directory; it can otherwise import another
checkout's package.

Keep mutable progress documents as observations when the product does not use
them as validation inputs. Do not turn actual runtime input drift into an
observation to rescue a failed run. If activation changes, retain the failure,
select a new candidate explicitly and rerun dependent comparisons.

Report fresh-process import/setup time, first verification, same-batch reuse,
final sweep and complete process wall separately when instrumented; otherwise
mark that phase unmeasured while retaining it in the total. Do not invent a
phase breakdown from residual wall time. OS filesystem caches are not
cold merely because the Node process is new. Compare full descriptor/output
hashes and all non-optimized code/input bindings; an in-memory overlay must also
bind the actual executed replacement code. State that an overlay is uninstalled.

## Reuse only within the verified lifetime

For the existing admission reader, prefer a small explicit scope around one
complete formal operation or a bounded sequential **read-only** offline batch.
All preparation writes finish before entering that scope. Never enclose
registration or proof/host changes, and never keep the scope across independent
HTTP requests. Batch gains require that actual batch consumer; they do not prove
single-request navigation or browser gains.

Reuse only the already validated size/digest after the same physical-path,
ordinary-file, current metadata and requested-pin checks. Keep public file/JSON
reads fresh. Retain the complete semantic checks, canonical dispatch comparison,
index/host/registry postflight and final stable-input sweep. Clear/close the scope
in finally; nested calls share the owner lifetime, siblings remain isolated and
detached work after closure fails. Do not cache descriptors or acceptance results.

Test the changed lifetime with actual readers: same-size edits, edit/revert,
byte-identical rewrite, symlink/hardlink substitution, conflicting pins, final
stage mutation, regenerated registry drift, nested calls, overlapping requests,
error cleanup and detached callbacks. Output equality and those negative checks
support this helper boundary; they do not close browser or acceptance gates.

## Integrate the whole input contract

Before editing a formal reader, enumerate every proof/host that owns its pin and
the preserved legacy inputs. One shared file can be pinned by several page proofs.
Choose successor proof paths before generating the final readers, then prepare
matching proof/host/index/activation changes under the existing single writer.

Preserve proof-owned versus host-owned inputs unless a reviewed change requires
moving ownership. With the current common reader, changing a proof-owned direct
pin while retaining its legacy input requires a matching
`host.legacyInputTransitions` entry: exact `original`, immutable byte-identical
`snapshot`, and `current` equal to the new covered pin. Keep original-path entries
unambiguous; preserve existing originals/snapshots when advancing current pins.
`successorInputTransitions` alone does not satisfy this legacy check. Do not add
`replacedRoutes` exemptions or delete old closure inputs to make it pass.

Verify the prepared transaction in isolation, then use the current guarded
installer with freshly checked preimages. Preserve a transaction-level rollback
record. Roll back only if the installed after-state still matches; a later writer
requires an explicitly prepared inverse successor, not a blind reverse patch.
The exact old installer, host number or experiment snapshot is not a current
installation instruction.

Use a short, non-counting My Lesson diagnostic before the costly formal package
when investigating a product failure. After the installed change is stable,
run the required full admission/semantics and relevant type checks, then
the affected frozen My Lesson, EN/ES, lifecycle, narrow-layout, resource and
negative-route assertions. Preserve earlier timeouts and skipped cells. Reuse
unchanged source facts claim by claim; a passing descriptor does not establish
current language exit, audio-owner cleanup, image review or navigation.

## Decision and evidence

Adopt a measured local optimization only for its tested consumers and segment;
expand after the next real consumer proves the same contract. Keep production
integration and browser verification as explicit next gates when the research
scope allows only an isolated patch. Estimate deadline feasibility from complete
delivery throughput at the requested named gate and known/unknown debt, never
by multiplying it by a local benchmark ratio. Use technical CLOSED only when
that is the requested gate. Follow the improvement into the next real lesson
or batch and record net new placements, playback outcomes, elapsed time and
remaining blockers in the existing checkpoint. Until then, report it as a
helper improvement with zero page credit; do not start another optimization
study merely because its benchmark passed.
